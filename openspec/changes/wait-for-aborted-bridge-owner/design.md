## Context

Bridge capacity and same-key admission waits share an in-flight creation marker.
On timeout the waiter already aborts that marker and cancels only its recorded
creator task. The marker intentionally remains registered until that creator
reaches its own finalization path, preventing an unsafe successor from
registering first.

## Goals / Non-Goals

**Goals:**

- Recover the timing-out request when the exact aborted owner terminates within
  one additional bounded admission wait.
- Preserve owner-held marker, handoff, drain, and structured-overload behavior.

**Non-Goals:**

- Change the global admission timeout, session capacity, or account routing.
- Remove a marker from a waiter, create a concurrent successor, or conceal a
  persistent owner failure.

## Decisions

- Reuse `_wait_for_http_bridge_aborted_owner` after each timeout handler has
  signalled abort. It verifies both the abort marker and exact task identity,
  then waits only for that task's termination.
- Bound the extra wait with the existing admission wait value. If it expires,
  re-raise the same structured 429 generated by the timeout path.
- Retry by continuing the enclosing admission loop only after the owner task
  has terminated. Its finalizer, not the waiter, removes or settles the marker.

## Risks / Trade-offs

- [An uncooperative owner adds one bounded wait before rejection] → retain the
  original 429 and use the existing timeout value; no unbounded retry occurs.
- [A premature marker release permits duplicate creation] → the waiter never
  removes the marker and tests assert no successor is created before owner
  termination.
